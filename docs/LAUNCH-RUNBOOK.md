# Ранбук запуску fox-armor.com.ua

Доповнює [MIGRATION.md](./MIGRATION.md): там інваріанти, тут — покрокова
послідовність дій. Стан на 06.09.2026: прод-інфраструктура розгорнута
(Neon + R2 + Resend + Vercel), сайт живе на https://fox-armor-ua.vercel.app,
URL-паритет 75/75, зона `fox-armor.com.ua` створена в Cloudflare у статусі
pending. Старий WordPress працює як працював.

Головний принцип: **день запуску = одна дія** (зміна nameserver-ів у
реєстратора). Все інше робиться заздалегідь і безпечно, бо спляча зона
нічого не змінює для живого сайту.

### 1.1. Домен — двофазне перемикання (рішення власника 07.09.2026)

Замість одного стрибка «нові NS → одразу Vercel» перемикаємось у дві
фази: непередбачуване вікно DNS-розповсюдження минає, поки обидві
сторони віддають той самий старий сайт, а справжнє перемикання стає
секундним і так само секундно відкочується.

**Фаза 1 — будь-коли до дня X; відвідувачі нічого не помічають.**
Зона в Cloudflare вже містить скопійовані записи старого хостингу.

1. ✅ 08.09.2026 — виконано крок `domain-attach` (`provision-ua-infra.ts`):
   `fox-armor.com.ua` і `www` додані до Vercel-проєкту і верифіковані
   (TXT не знадобився — той самий акаунт). Аудит зони: всі записи живого
   DNS скопійовані (apex A/AAAA, wildcard, MX `mx.services`, SPF) +
   Resend-набір; проксі Cloudflare на записах сайту вимкнено (DNS only),
   тож після активації зони відповіді DNS ідентичні поточним.
2. ✅ 16.09.2026 — власник замінив nameserver-и в панелі adm.tools
   (`ns17/ns27/ns37.inhostedns.*` → `annalise` + `rajeev
   .ns.cloudflare.com`). WHOIS і делегування реєстру оновилися за
   ~годину.
3. ✅ 16.09.2026 — зона **Active**. Перевірено: нові NS віддають
   ідентичні записи (apex A/AAAA, MX `mx.services`, SPF), сайт віддає
   200 зі старого nginx, публічні резолвери бачать той самий IP.
   Перемикання пройшло непомітно. У панелі adm.tools НЕ натискати
   «Установить» у блоці «Наши NS» — це відкат делегування.

**Фаза 2 — день X.** Змінити в зоні A/AAAA апекса і `www` зі старого
хостингу на Vercel. TTL у Cloudflare малий — зміна доїжджає за
секунди-хвилини; відкат — повернути записи назад (старі значення скрипт
друкує при видаленні), так само за секунди. Найкраще перемикатись у час
низького трафіку. Крок відмовиться працювати, поки зона не Active:

**Куди що створювати, щоб усе зв'язалося.** Зв'язуються між собою лише три
сервіси Google: GA4 ↔ Google Ads ↔ Search Console. Правило одне: один
Google-акаунт (власника бізнесу, не підрядника) має бути адміном у всіх
трьох. Тобто GA4 property створювати з того самого Google-акаунта, який
адмініструє Ads-акаунт `AW-16613578416` і є verified-власником
fox-armor.com.ua у Search Console. Потім у GA4: Admin → Product links →
Google Ads і Search Console. Meta Pixel (Business Manager) і TikTok Pixel
(Ads Manager) — окремі світи, з Google не зв'язуються; ті самі ID просто
продовжують працювати.

Акаунт Ads, кампанії, Search Console — не чіпаються взагалі: домен той
самий, тег той самий.

**Очікуване «просідання», яке не є поломкою:** WP вантажив трекери всім
одразу, наш код — лише після згоди (consent-банер). Кількість зафіксованих
відвідувань у GA4/Pixel впаде відносно WP; конверсії Ads рахуються з
Consent Mode v2. Це законна поведінка, не баг.

даними.)

**Свіжі дані без деплою.** Кеш даних Vercel переживає повторні деплої
того самого коміту, тому після будь-якої зміни даних поза застосунком
(порт-скрипт, ручний SQL — наприклад, порядок хітів `featured_order`)
каталог оновлюється службовим ендпоінтом:

```bash
cd /Users/z1maka/Projects/fox-armor-ua && curl -s -X POST https://fox-armor-ua.vercel.app/api/revalidate/ -H "x-revalidate-secret: $(grep -E '^REVALIDATE_SECRET=' .env.production | cut -d= -f2-)" -H "Content-Type: application/json" -d '{"tags":["catalog"]}'
```

Секрет лежить у `.env.production` (`REVALIDATE_SECRET`); без нього роут
відповідає 403. Після дня X команда та сама, лише домен основний.

## 2. День X — послідовність

Передумова: фаза 1 з §1.1 зроблена (зона Active, домен верифікований у
Vercel), сайт ще показує старий WordPress.

1. **Прогнати паритет ще раз:**
   `pnpm tsx scripts/verify-url-parity.ts https://fox-armor-ua.vercel.app`
   — має бути 75/75.
2. **Фаза 2 з §1.1:** перемкнути A/AAAA-записи апекса і `www` у зоні
   Cloudflare зі старого хостингу на Vercel (`domain-flip`). Доїжджає за
   секунди-хвилини. Vercel випустить сертифікат одразу, як побачить
   трафік (домен уже верифікований TXT-ом).
3. **Перевірки одразу після перемикання:**
   - `https://fox-armor.com.ua/` відкривається з валідним сертифікатом,
     `www` редіректить на апекс;
   - `pnpm tsx scripts/verify-url-parity.ts https://fox-armor.com.ua` — 75/75;
   - Resend: домен став verified (кабінет), тестовий лист доходить;
   - тег Ads і Pixel стріляють (Tag Assistant / Pixel Helper);
   - вхідна пошта домену (якщо є скриньки на хостингу) працює — MX
     скопійований у зону як був.
4. **Відкрити індексацію** — єдине справжнє «поміняти назад»:
   в env Vercel поставити `SITE_INDEXABLE=true` + redeploy. До цього
   robots.txt навмисно віддає `Disallow: /`. Забути цей крок = Google
   почне викидати сторінки з індексу. Після redeploy перевірити
   `curl https://fox-armor.com.ua/robots.txt`.
5. **Прибрати `ADMIN_BASE_URL`** з env Vercel (+ redeploy). До дня X вона
   тримає адмінські посилання в Telegram на `fox-armor-ua.vercel.app`, бо
   домен ще віддає старий сайт і посилання на `/admin/orders/...` ловить
   його 404. Після перемикання адмінка живе на самому домені, і змінна
   стає зайвою: без неї посилання будуються з `NEXT_PUBLIC_SITE_URL`.
6. **Search Console:** нічого не переналаштовувати (той самий домен і
   property). Лише відправити sitemap повторно: обидві адреси
   `/sitemap.xml` і `/sitemap_index.xml` мають віддаватися.

## 4. Відкат

Після фази 2 — повернути A/AAAA-записи в зоні Cloudflare на старий
хостинг: WordPress повертається за секунди. Крайній варіант (проблеми з
самою зоною) — повернути nameserver-и в реєстратора на
`ns17/ns27/ns37.inhostedns.*`. Більше нічого відкочувати не треба: базу,
сховище і деплой нового сайту відкат не руйнує, спроба №2 можлива у
будь-який момент.
